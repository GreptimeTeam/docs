# 容量规划

写入行数或 QPS 与 CPU、内存、存储之间没有固定换算关系。行宽、Tag 基数、查询时间范围、聚合开销、索引配置、Compaction 和流量突增都可能显著改变资源需求。生产环境应使用有代表性的工作负载进行压测，再结合生产指标验证容量是否足够。

## 描述工作负载

压测前至少记录以下输入：

- 平均和峰值写入行数、平均行大小、流量突增持续时间
- 表和 Region 数量、Tag 基数、Schema 变更频率
- 并发查询数、扫描时间范围、过滤条件、聚合方式、结果集大小
- 数据保留时间和预期增长速度
- 可用性目标，以及节点或故障域不可用后必须保留的容量

压测数据应接近生产数据。均匀生成的测试数据通常具有不同的压缩效果，也无法覆盖真实的索引负载。

## 规划计算和内存

不同组件的瓶颈不同：

- Frontend 使用 CPU 和网络资源接收请求、规划分布式查询并合并结果。
- Datanode 负责写入、查询、Compaction、索引和缓存，其 CPU 和内存需求取决于这些任务的组合。
- Metasrv 的资源使用主要取决于集群元数据和控制面操作，而不是数据量本身。

不要按固定比例为读写分配 CPU，也不要假设固定的 CPU 与内存比例。压测时应同时运行写入和查询负载，并覆盖峰值并发；观察 CPU 饱和度、内存使用、请求延迟、Compaction 积压和缓存状态。相关配置和指标参见[性能调优](/user-guide/deployments-administration/performance-tuning/performance-tuning-tips.md)。

## 规划存储

先估算未压缩的逻辑数据量：

```text
每日逻辑数据量 = 平均每秒行数 × 平均每行字节数 × 86,400
保留期逻辑数据量 = 每日逻辑数据量 × 保留天数
```

这个结果不是实际需要的物理容量。压缩、Compaction、索引和对象存储实现都会影响实际占用，不能套用统一的压缩比。应使用有代表性的数据测量实际物理大小。

分别计算各存储层的容量：

- 用于 SST 和索引文件的对象存储或本地数据存储
- 使用 Local WAL 时的本地 WAL 空间
- 使用 Remote WAL 时的 Kafka 容量和保留时间
- 本地缓存和索引暂存空间
- Compaction 和业务增长所需的临时余量
- 容灾方案所需的备份空间

如需限制数据保留量，请为表设置 TTL。参见[使用 TTL 管理数据保留](/user-guide/manage-data/overview.md#使用-ttl-策略保留数据)。

## 验证容量规划

使用生产计划采用的 Schema、索引和存储后端进行测试。测试至少覆盖：

1. 稳态写入和预期的查询组合。
2. 写入峰值、查询并发峰值及两者重叠的情况。
3. 流量持续期间的 Compaction 和索引创建。
4. 如果容量规划包含故障容忍能力，测试节点故障或维护事件。
5. 运行足够长的时间，以暴露缓存抖动和后台任务积压。

结合 [GreptimeDB 监控](/user-guide/deployments-administration/monitoring/overview.md)和基础设施指标判断结果。为负载波动和故障恢复保留余量；Schema、索引、查询、保留时间或硬件发生重大变化后，重新进行压测。
